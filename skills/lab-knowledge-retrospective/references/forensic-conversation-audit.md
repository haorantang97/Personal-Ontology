# 逐轮法证审计协议

本协议只在 `lab-knowledge-retrospective` 的法证模式中启用。目标不是生成更长的摘要，而是证明复盘确实覆盖了范围内每个实质性问答，并能把错误响应、用户纠正、后续后果和根因连接起来。

## 1. 先建立材料清单

列出复盘范围内的：

- 当前任务和所有被用户明确称为同一项目、关联窗口、交接来源或执行分支的任务。
- 原始用户消息、Agent 回复、工具调用与结果。
- 被提及的文件、报告、测试记录、截图、计划和状态标记。
- 可能只记录最终状态的摘要、HANDOFF 或进度文档。

原始轮次是一手过程证据。摘要、HANDOFF 和最终报告是二手定位材料，不能证明某一轮确实得到回答，也不能证明某项动作确实执行。

若可用任务读取工具支持分页，持续读取到起点。对每个关联任务记录 `已读到起点 / 只读到部分 / 无法访问`。对话压缩后的上下文不等于原始历史。

### 关联任务消歧与访问尝试

不能只凭相似标题任选“另一个任务”。优先使用用户给出的任务 ID、原始标题、项目路径、明确引用和时间关系；没有唯一标识时，先通过可用的任务列表与摘要找候选，再读取候选原始轮次验证它是否包含用户所指的共同项目证据。仍有两个以上合理候选时，向用户确认；若本轮必须先交付，则把该范围记为缺失并强制 `PARTIAL`。

在把历史标记为“无法访问”前，记录已尝试的可用只读路径：任务列表或索引、目标任务读取、旧轮次分页，以及用户已经放入范围的本地交接材料。交接材料只能辅助定位和界定缺口，不能补充成不存在的原始轮次。某一次读取失败不足以证明全部历史不可访问；只有当前可用的安全只读路径都已尝试后才能降级。

## 2. 划分实质性用户轮次

使用两遍扫描建立分母：

1. **发现遍**：从范围起点读到终点，为每条原始用户消息分配稳定 ID（例如 `M001`），并登记为“实质性来源消息”或“排除消息 + 理由”；此时不评价回答质量。一条实质性来源消息包含多个独立要求时，再分配要求单元 ID（例如 `M001.a`、`M001.b`）。
2. **审计遍**：只对发现遍得到的全部实质性要求单元核验响应并给出判定，不得在审计遍重新挑选分母。

发现遍结束时必须先计算并冻结以下分母：

- `原始用户消息数 = 实质性来源消息数 + 排除消息数`。
- `实质性要求单元发现数` 等于所有实质性来源消息拆出的要求单元总数。
- `纠正发现数`、`声明发现数` 和 `未闭环发现数` 分别来自对应的全量发现遍，而不是事后挑出的重点。

实质性要求单元总数必须来自发现遍，不能从已经挑选出来的“重要节点”反推，否则 `发现数 == 审阅数` 没有意义。

以下内容各算一个实质性轮次；一条消息包含多个独立要求时，拆成多个子项：

- 请求、问题、验收标准或约束。
- 对事实、范围、优先级、偏好或方法的纠正。
- 质疑、反例、风险提醒或要求核验。
- 批准、拒绝、暂停、恢复、范围变更或完成判定。
- 状态追问，只要它要求 Agent 对执行情况作出事实声明。

通常不单独计入：自动注入的 UI 状态、重复附件元数据、无决策含义的寒暄或纯确认。但如果“可以”“停一下”“已登录”等消息授权了动作、改变了状态或关闭了阶段，就必须计入。

## 3. 建立逐轮账本

对每个实质性轮次至少登记：

| 字段 | 要求 |
|---|---|
| 定位 | 任务标识、稳定消息 ID 与要求单元 ID；有原始 ID 时一并保留 |
| 用户要求 | 原意；多要求消息要拆项 |
| Agent 响应 | 回答了什么、承诺了什么、执行了什么 |
| 证据 | 工具结果、文件、测试、外部来源或用户确认 |
| 后续纠正 | 后面是否被用户否定、收窄、扩展或追问 |
| 响应质量 | 从下方固定枚举中选择 |
| 后果 | 是否导致返工、错误架构、额外成本、错误信心或遗漏 |
| 当前状态 | 已闭环、部分闭环、未闭环、被明确取代 |

固定响应质量枚举：

- `supported`：回答和行动有充分证据，满足该轮要求。
- `partially_supported`：只完成部分要求或证据不完整。
- `unsupported`：给出事实或结论，但证据不足或后来被否定。
- `premature_completion`：在验收标准未满足时声称完成、跑通或验证。
- `unanswered`：没有实质回应，或回应绕开了问题。

生命周期单独记录在“当前状态”字段，固定为：`已闭环`、`部分闭环`、`未闭环`、`被明确取代`。同一要求单元可同时具有一个响应质量和一个生命周期状态；后续换方向只会改变生命周期，不能抹掉早先回答的质量。例如，过早声称完成的要求后来被用户放弃，仍应记录为响应质量 `premature_completion`、当前状态 `被明确取代`。

同一轮可拆分后使用不同响应质量。不得用后续做对的事情倒推前一轮已经答对。

## 4. 建立声明账本

先从范围内全部 Agent 回复做一次声明发现遍，再核验。找出所有会改变用户判断或后续行动的重要声明，特别是：

- “已完成、已修复、已接通、已经跑通”。
- “测试通过、已经验证、不需要登录、可以稳定运行”。
- “这是根因、这是官方数据、这是最成熟方案”。
- “已经执行某个 Skill、已经读取全部历史、已经写入或标记进度”。

每项声明必须标记为：`已证实 / 仅部分证实 / 无证据 / 被反证`，并指向具体证据。只有文件存在不等于功能可用；只有一次成功不等于稳定；只有最终状态摘要不等于执行过程完整。

凡用户点名要求核验的措辞或声明类别，例如“所有已验证、已跑通”，其在范围内的每个匹配实例都必须进入账本，不受 Agent 对“重要性”的主观筛选。覆盖声明同时报告 `声明发现数 / 声明核验数`；两者不相等时只能为 `PARTIAL`。

## 5. 建立纠正账本

逐一登记用户纠正：

1. 它纠正了哪一轮、哪个事实或哪个假设。
2. Agent 下一轮是否明确承认并更新模型。
3. 后续设计、代码、测试或结论是否真正改变。
4. 同一错误是否再次出现。

如果 Agent 口头同意，但后续仍按旧假设执行，判定为“未吸收”，不能写成已闭环。

## 6. 建立未闭环账本

主动寻找四类遗漏：

- 用户提出但 Agent 没有回答。
- Agent 提出选择或问题，但用户没有确认，Agent 却替用户决定。
- Agent 只回答了表面问题，没有处理用户给出的验收标准。
- 后续方向变化掩盖了先前未完成事项，但用户没有明确撤销它。

每项标记 `仍有效 / 已被用户撤销 / 已被新方案取代 / 无法判断`。不要把“对话后来讨论了别的”当作自动关闭。

## 7. 构建根因链

对主要失败至少区分四层：

1. **直接错误**：某一轮漏答、误判、无证据承诺或过早完成。
2. **执行流程**：缺少什么检查、状态机、验收或回读动作。
3. **Skill/编排**：触发条件、模式选择、参考文件、硬性门槛或完成定义是否允许跳步。
4. **环境与证据**：历史不可见、工具受限、外部平台变化等是否真实构成限制。

Skill 有缺陷与 Agent 未执行不互斥。若旧 Skill 的文字允许跳过逐轮覆盖，应明确为结构性根因；若 Skill 已有硬门但 Agent 违背，则是执行违约。不要用单一归因掩盖共同原因。

## 8. 硬性覆盖门

在蒸馏候选结论前逐项核对：

- `原始用户消息数 == 实质性来源消息数 + 排除消息数`。
- `实质性要求单元发现数 == 实质性要求单元审阅数`。
- 每个多要求消息的子项都有判定。
- `纠正发现数 == 纠正已关联数`，且每次用户纠正都链接到原回答，并检查是否被吸收。
- 每项重要完成声明都已分类并有证据指针。
- 用户点名的声明类别已全量扫描，且 `声明发现数 == 声明核验数`。
- `未闭环发现数 == 未闭环已分类数`。
- 每个关联任务都已读到起点；任何只读到部分或无法访问的任务都已列出，并自动强制结果为 `PARTIAL`。
- 最终结论没有使用未审阅范围作为证据。

全部满足且不存在任何历史缺口时才可报告 `COMPLETE`。任一不满足或任一关联任务未读到起点即为 `PARTIAL`。不得用“大体完整”“基本覆盖”模糊替代。

如果为 `PARTIAL`：

- 说明已覆盖的任务、轮次和时间段。
- 说明缺失内容及其对判断的影响。
- 不对缺失部分下全项目结论。
- 可以输出证据完全位于已审阅范围内的窄结论，但必须写明边界。

## 9. 最终输出压缩原则

账本负责完整，报告负责可读。用户没有要求逐轮明细时，最终报告只需呈现：

- 覆盖声明和缺失范围。
- 最重要的错误轮次、转折、纠正和后果。
- 根因链与可复用结论。
- 仍未闭环的问题。

若用户明确要求“复盘每一次问答”，则按任务或阶段分组展示逐轮结果；可以压缩措辞，但不能省略任何实质性轮次。
