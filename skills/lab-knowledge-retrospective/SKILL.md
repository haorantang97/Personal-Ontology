# Lab Knowledge Retrospective

把已经结束的一段工作变成有证据、有边界、能改变未来行动的结论。默认结果可以为零；不要为了显得有收获而制造规律。

本 Skill 内置稳定的审计协议；具体领域的方法仍从知识库的 `methods/` 页面读取。方法页可以补充判断框架，但不能削弱本 Skill 的逐轮覆盖、证据和审批门槛。

## 1. 先过触发门

### 结束或暂停状态

仅在以下任一条件成立时继续：

- 用户明确说任务结束、阶段结束、先到这里、项目暂停、项目失败或开始复盘。
- 目标已达成并有可验证结果，当前只讨论可复用经验。
- 一次事故已经关闭，当前要复盘过程；根因可以仍有竞争解释，但必须明确标为未确认。
- 长对话中的一个清晰阶段已经关闭，即使整体项目仍继续。

如果工作仍在推进，且用户当前需要的是查明故障或完成修复，停止本 Skill 并继续调查；不要用复盘替代执行。但当用户已经明确暂停、判定失败或关闭当前阶段时，即使根因尚未完全确认，也可进入法证模式，把已证实原因、竞争解释和未知项分开。

### 复盘意图

本 Skill 关注“以后遇到类似情况怎么判断或行动”。如果用户只要时间线、会议纪要、聊天摘要或续工检查点，直接满足或交给对应工具，不把它包装成知识复盘。

## 2. 范围预检

在选择模式之前，先检查当前可见材料，而不是凭当前上下文的长度猜测完整性。至少记录：

- 当前上下文是完整原始历史、经过压缩/截断，还是完整性未知。
- 用户是否提到关联任务、其他窗口、HANDOFF、交接材料或同一项目的执行分支。
- 当前可见范围是否出现纠正、质疑、批准、撤回、完成声明或“已验证/已跑通”等事实声明。
- 当前宿主是否提供读取当前任务与关联任务原始历史的安全只读路径。

只有能够确认范围短、历史完整且不存在法证触发条件时，才允许进入结论模式。上下文经过压缩、截断、完整性未知，或尚不能排除隐藏的纠正、完成声明和关联任务时，默认进入法证模式；初始覆盖状态记为 `PARTIAL`，直到原始历史读取和硬性覆盖门证明可以升级为 `COMPLETE`。不得因为当前可见片段看起来很短，就直接选择结论模式。

## 3. 选择复盘模式

先选模式，再收集证据。模式影响审计深度，不能在输出前临时降级。

### 结论模式

仅用于范围短、目标单一、没有多次纠正，且用户只关心最终结果与可复用经验的阶段。可以围绕关键节点复盘，不要求逐轮列账。

### 法证模式

出现以下任一条件时必须使用法证模式：

- 用户要求“深度复盘”“复盘每一次问答”“逐轮检查”“为什么会漏答、偏航或误判”。
- 项目失败、被暂停或被用户判定为暂时失败。
- 长对话，无论最终报告是否要求简洁。
- 长对话包含多次换方向、纠正、质疑、批准、撤回或完成声明。
- 复盘范围跨越两个或更多关联任务、聊天或交接文档。
- 需要判断 Agent 是否真的执行了某个 Skill、测试、核验、修改或交付。

长对话或失败项目存在歧义时，默认选择法证模式。选择法证模式后，现在就完整读取 [逐轮法证审计协议](references/forensic-conversation-audit.md)；在后续范围、账本和覆盖步骤中按该协议执行。

不得因为最终报告需要简洁，就把法证模式降级为结论模式。简洁只约束呈现，不约束审计覆盖。

## 4. 取得当前方法

在正式蒸馏前调用 `agent-knowledge` MCP 的 `knowledge_route`，按事件类型和当前目标查询可复用方法：

- `action=read`：使用 `knowledge_get` 按返回的精确 slug 完整读取 selected 页面，只在页面声明的证据、适用范围与失效条件内使用。
- `action=review`：只表示存在弱候选，不得把候选标题或摘要当成事实；需要时继续用结果层搜索并完整读取选中页面。
- `action=none`：继续执行本 Skill，不虚构现成方法。
- `retrieval.status=unavailable` 或工具报错：明确方法网关当前不可用，继续做有边界的复盘，但不得声称已成功检查方法库。

常见查询方向包括：任务卡住或目标没达成、访谈或长对话蒸馏、工具或写入故障、证据边界和表达形态。不要把这些示例当作固定页面名，也不要仅凭记忆复述旧方法。

## 5. 锁定范围与原始证据

写下本轮范围：

- 起点与终点。
- 原始目标和验收标准。
- 实际结果。
- 本轮允许使用的任务、对话、文件、运行结果和用户确认。
- 明确排除的其他阶段、私密材料和第三方信息。

如果在这里发现对话经过压缩、缺少关键消息或无法确认完整性，立即切换为法证模式并保持初始覆盖状态为 `PARTIAL`；不要补写不可见过程，也不要继续以结论模式交付。

法证模式必须先找出范围内全部关联任务，并尽力从起点读取原始用户消息、Agent 回复、工具结果、文件与运行证据。任务摘要、HANDOFF、状态说明和最终报告只能帮助定位，不能代替原始轮次。若工具允许分页读取旧轮次，就持续读取到起点；若仍无法取得完整历史，覆盖状态必须为 `PARTIAL`，并准确列出缺失范围。

发现密钥、令牌、账号信息、无关私人材料、Raw 访谈或未经授权的第三方信息时，不在复盘输出中复制，也不送入知识库候选。

## 6. 建立审计账本

结论模式先在内部整理：目标与预期、可验证结果、关键动作、失败与偏差、用户纠正、根因状态和未解决项。

把 Agent 自己声称“已完成”“已验证”“这是根因”的话视为待核验陈述。实际产物、测试结果和用户确认优先。

法证模式必须按参考协议建立：

- 逐轮账本：每个实质性用户轮次都要有去向和判定。
- 声明账本：逐一核验“完成、验证、接通、运行、已修改”等实质性声明。
- 纠正账本：把每次用户纠正连接到原回答，并判断后续是否真正吸收。
- 未闭环账本：找出未回答、只答了一半、被擅自替用户决定或被后续工作掩盖的问题。

账本默认只保留在模型工作记忆中。确需物化时，只能使用宿主提供的任务临时区或 scratch 区，尽量少复制原始文本，并在最终回答前清理；不得持久化或自动摄取原始历史。用户没有要求完整逐轮表时，最终报告无需机械复述全部聊天。但不得在账本完成前直接跳到经验总结，也不得把账本或原始对话自动写入知识库。

## 7. 通过覆盖门

结论模式至少要确认：目标、结果、关键证据、用户纠正和未解决项都有来源。

法证模式必须先通过参考协议中的硬性覆盖门：原始用户消息全部登记为实质性来源或带理由排除；实质性要求单元发现数与审阅数一致；每次用户纠正已关联；每项重要完成声明已核验；每个未闭环项已分类；范围内关联任务已读取到起点。

只允许两种覆盖结论：

- `COMPLETE`：硬性覆盖门全部通过，且不存在历史缺口。
- `PARTIAL`：任何一项未通过、历史不可访问或关联范围仍缺失。

`PARTIAL` 必须说明已经审阅什么、缺少什么，以及哪些判断因此不能成立。不得把未审阅部分蒸馏成跨全项目结论；只可保留证据完全落在已审阅范围内、且边界写清楚的窄结论。

覆盖状态描述的是证据范围，不是项目成败，也不是本次报告是否已经交付。允许“复盘报告已交付、覆盖状态为 `PARTIAL`”，但不得把它简称为“复盘完整完成”。

## 8. 蒸馏候选结论

把事件叙述改写成可迁移候选：

- 叙述：“这次出现 X，后来做了 Y。”
- 候选结论：“在条件 A 下看到 X 时，先做 Y，因为证据 Z；条件 B 出现时该规则失效。”

每条候选至少包含：

- **结论**：未来应如何判断或行动。
- **证据**：具体对话、文件、运行、数据或用户原话。
- **样本量**：明确写 `n=1`、`n=2` 或实际范围。
- **适用范围**：什么条件下成立。
- **失效条件**：何时不能套用。
- **置信度**：高、中或低，并说明原因。
- **未来影响**：它会改变哪个回答、判断或动作。
- **候选去向**：仅留在对话、作为证据材料、更新已有知识页、新建知识页或不收录。

遵守以下边界：

- `n=1` 可以形成窄范围、带版本或场景限定的操作结论，但不能写成普遍规律。
- 先后发生不等于因果；根因未证实就标记为假设。
- 单次用户纠正可以约束当前任务，不能自动升级为全局偏好。
- 稳定能力、行为模式、价值观或个人偏好至少需要两个独立事件、一个主动寻找的反例或竞争解释，并由用户确认。
- 不诊断人格、心理、健康或关系，不推断第三方动机。
- 用户确认的最终选择高于 Agent 草稿；保留被否定方案仅用于解释边界，不把它继续当作现行结论。

## 9. 通过收录门槛

只有同时满足以下条件，才建议进入长期知识候选：

1. 未来仍会在决策或执行中使用。
2. 会改变 Agent 的回答、判断或动作。
3. 已形成相对稳定的结果，不只是过程、情绪或素材堆积。
4. 能写清证据边界、样本量、适用范围与失效条件。
5. 不是现有知识的小幅重复；若能更新已有页面，就不新建。
6. 权限允许长期保存及预定用途。

默认产出为零。没有候选通过全部门槛时，明确报告“本轮无可沉淀结论”，并说明主要原因。事件过程不能伪装成结果页；只有当正式结论需要可追溯证据且用户授权时，才可把必要过程路由为证据层。

## 10. 输出复盘审计

用户明确要求复盘时，输出：

1. **覆盖声明**：模式、覆盖状态 `COMPLETE/PARTIAL`、纳入的任务、原始用户消息总数、实质性来源消息数、排除消息数、实质性要求单元发现数/审阅数、纠正发现数/已关联数、完成声明发现数/核验数、未闭环发现数/已分类数和缺失范围。结论模式可省略计数，但不能省略模式与证据边界。
2. **复盘范围**：本次覆盖与不覆盖什么。
3. **已确认结果**：只写有证据的事实。
4. **关键转折与逐轮问题**：法证模式下说明最重要的漏答、误判、过早完成、错误承诺、纠正未吸收及其后果；用户要求“每一次问答”时，按任务或阶段展示全部实质性轮次。
5. **根因链**：区分直接原因、执行流程、Skill/编排原因和证据仍不足的假设。
6. **可复用候选**：逐条写结论、证据与样本量、适用与失效条件、置信度、未来动作和候选去向。
7. **不收录内容**：列出被排除的主要候选及理由。
8. **未解决项**：明确仍需调查或下一阶段处理的内容。
9. **知识库动作**：不入库、等待用户决定是否准备提案，或展示精确待审批提案。

保持最终呈现紧凑。不要把完整聊天记录机械复述一遍，也不要用空泛的“沟通很重要”“以后更谨慎”充数。这里禁止的是冗长输出，不是逐轮审计。

## 11. 可选交接知识库

本 Skill 可以独立完成复盘；知识库写入是可选后续，不是复盘成功的必要条件。

### 用户一开始就要求入库

在任何知识库变更工作之前，把通过门槛的候选明确交给 `lab-knowledge-intake`；由 Intake 先调用 `agent-knowledge` MCP 的 `knowledge_intake`，再读取当前机器 Schema、目标页面和同类型有效页面，完成格式、枚举与双向关系预检。复盘 Skill 不自行猜测 frontmatter，也不把项目“暂停/失败/完成”等业务生命周期直接写入 Schema 的 `status` 字段。

只有 `knowledge_propose_changes` 返回成功并生成精确 Proposal ID，才可说“已进入提案”。提案创建或批准后应用若被校验拒绝，必须明确说明知识库没有修改，并交回 Intake 按当前契约重建提案；旧批准不能转移。

### 用户只要求复盘

不要自动创建待审提案。先交付复盘审计；有合格候选时，询问用户是否要准备知识库提案。用户同意准备后交给 `lab-knowledge-intake` 执行当前契约和提案预检，再生成精确提案并单独等待审批。对候选结论的认可不等于对尚未展示的文件变更授权。

### 网关不可用

只交付复盘审计并停止。不要直接编辑 Vault、Git、GBrain、Schema 或提案文件，不要退回到无人管理的 Markdown 文件。

## 12. 完成标准

只有同时做到以下事项才算完成：

- 范围明确，已检查结束或暂停状态与复盘意图，并在模式选择前完成范围预检。
- 已明确选择结论模式或法证模式；法证模式已执行逐轮协议并报告 `COMPLETE/PARTIAL`。
- 结果、叙述、根因假设和长期结论已分开。
- 法证模式下，每个实质性用户轮次、用户纠正、重要完成声明和未闭环项都已登记或明确标记为不可访问。
- 每条候选都有证据、样本量、适用与失效条件。
- 未达到门槛的内容已明确排除。
- 进入知识库流程时，已由 Intake 按当前机器 Schema、目标文件格式与双向关系完成提案预检；未把业务生命周期误写入受限的 Schema 状态字段。
- 未经批准没有发生知识库写入。
- 输出能让下一个 Agent 在相似条件下采取更准确的行动。
