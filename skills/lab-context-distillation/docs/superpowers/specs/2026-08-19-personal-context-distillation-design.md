# Personal Context Distillation 设计规范

日期：2026-08-19
状态：已批准方向的独立实现规范；2026-08-20 按完整实现审计修订

## 1. 目标

构建一个可公开查看、可在 Codex/Claude 一类支持 Skill 的代理环境中运行的个人上下文蒸馏 Skill。它把用户授权的本机聊天资料，经本机采集、快照、规范化、脱敏和证据封存后，交给用户当前模型完成 Map、跨事件归并和最终蒸馏；所有结果再由本机确定性验收、修复和人工裁决。最终知识库写入必须单独批准。

产品不是聊天导出器，也不是履历抽取器。它要形成带证据边界的“个人运作模型”：表达习惯、思考路径、价值取舍、行为模式、盲点、反例、代价和时间变化。

## 2. 硬边界

- 仅覆盖 macOS 微信 4.x 与 Windows 微信 4.x；平台连接器采用适配器接口。
- 不做 GUI。产品由 `SKILL.md`、确定性脚本、参考文档、合成 fixture 和测试构成。
- 原始数据库、密钥、身份映射永远只在本机可信边界中。
- 发送给模型的必须是已脱敏 release 数据包。
- 模型、厂商、型号和代理数量均不写死；只按任务风险建议普通/高级能力档和动态并发。
- 没有 Fast 开关。吞吐优化不能绕过隐私门、依赖门、验收或 receipt。
- accepted 是不可逆终态；新规则或新模型需要新 generation，不能原地重跑旧 accepted。
- release、manifest、数据包哈希和 receipt 一经封存不可修改。

## 3. 授权模型

三种动作需要不同门槛：

1. 用户要求分析或蒸馏：视为授权当前任务处理已经脱敏的数据。
2. 新增数据源，或要把未脱敏原文发给模型：必须再次确认。
3. 任何知识库写入：必须展示提案及数字封条后，由用户明确批准。

本机发现、只读快照、规范化和脱敏属于当前任务的正常实施步骤；可选密钥获取仍需单独的本机秘密授权 receipt。

## 4. 核心数据流

```text
授权 → 只读发现 → 一致快照 → 解密/导入 → 统一记录 → 本机脱敏
  → 冻结 release → Map 数据包 → 模型输出 → 本地验收/修复
  → 跨事件归并 → 冲突补漏 → 最终蒸馏 → 质量审计/人工裁决
  → 知识库提案 → 用户批准 → 外部写入
```

模型工作与本地工作通过不可变文件交换，不共享密钥、身份映射或源库路径。

## 5. 数据契约

### 5.1 Source row

每个源行产生本地 locator 和 fingerprint。覆盖率按 fingerprint 集合计算，不能只比较总数，也不能因为内容相同而去重。

### 5.2 Unified record

统一记录至少包含：

- 稳定 `record_id`；
- `source_fingerprint` 和本地 locator；
- 时间、平台、会话和发送方向；
- sender/author/quoted_author 的独立边界；
- `authored_text`、`quoted_text`、`forwarded_context`；
- 媒体类型和可用性；
- redaction 状态和证据精确度。

### 5.3 Evidence contract

模型结论必须引用 release 内的 `record_id`，并标记证据类型：观察行为、自述、他述、引用、转发或未知。修复只能降低来源强度，不能升级，也不能创造证据。

### 5.4 Release

release 目录使用 staging 构建，全部验收后原子发布。manifest 包含上游 fingerprint 集、记录数、缺口、schema 版本、数据包哈希和生成器版本。封存后只读；任何改变都产生新 generation。

## 6. 状态机

工作单元状态：

```text
pending → reserved → inflight → produced → validated → accepted
                       ├→ retry_infra
                       ├→ quarantined_content
                       ├→ blocked_dependency
                       └→ needs_human
```

追加账本是权威状态；汇总文件只是缓存。租约过期后可回收 reservation。已有输出只有在哈希和契约都通过时才能回收。`accepted` 不允许返回任何可运行状态。

## 7. 任务分层

- Map：逐片段形成证据候选，不做跨全局的夸大结论。
- Merge：跨事件归并同义、因果、矛盾、演变和缺口；完整 Map 仍然保留。
- Final：在依赖满足、候选集冻结后形成个人运作模型。
- QA：独立量表检验结构、证据召回、反例、负面模式、覆盖和过度推断。
- Adjudication：语义歧义、证据冲突、隐私例外或不可确定的结构问题由人处理。

## 8. 验收与自动修复

本地权威 validator 检查 schema、证据存在、覆盖、依赖、哈希、来源强度、精确度和泄密风险。传输 schema 只用于提高接口兼容性，不能替代本地验收。

自动修复采用白名单：字段形状、允许的 null/空值规范、稳定排序、重复 evidence id 去重、可推导的覆盖关系。任何会改变叙事、增加证据、升级来源强度或替用户裁决冲突的改动一律禁止。

## 9. 失败隔离与恢复

- 基础设施错误：限流、超时、5xx、进程中断、传输事件；指数回退或回收有效输出。
- 结构错误：先运行白名单编译器，再复验。
- 内容错误：隔离单元，不全局降并发。
- 隐私错误：立即阻断 release 或提交。
- 依赖错误：等待前置 receipt，不重试模型。

本地 feeder、validator 和 committer 分段运行。对话中断后通过账本恢复；后台持续性不是正确性的前提。

## 10. 超大任务与并发

按记录、事件和图组件边界拆包；不截断 JSON 记录，不无故切断强关联组件。若单组件超预算，先生成带完整 lineage 的紧凑派生视图，再继续分层；派生视图永不替代完整 Map。

并发是动态建议，不是固定值。状态报告必须区分目标并发、已保留、活跃、已完成、待验收和隔离。只有系统性基础设施错误影响全局并发；单个语义失败只隔离该单元。

## 11. 平台与解密实现

核心实现不包含、复制或重写任何受限微信解析源码。平台层现在实际实现：macOS/Windows 标准与显式目录发现、私有账户 registry、多库角色 inventory、SQLite/WAL backup、加密 DB/WAL/SHM 稳定集合快照、用户授权私有 key 文件、标准 SQLCipher 4 stdin/export、原子混合解密快照、schema fingerprint/profile、消息/联系人/群聊/媒体/Favorites/Moments 映射和 release-bound checkpoint。

进程内存 key 提取、注入、重签名和 proprietary key derivation 因 2026 年公开法律/terms 风险被明确排除。实现存在不等于真实 build 已兼容；两个 observed-shape profile 只在独立合成 fixture 上验证。安全回退仍是让用户提供合法已解密标准导出，而不是尝试未知写操作或上传源库。

## 12. 可公开性与 clean-room

公开包仅含合成数据。不会包含真实聊天、身份、密钥、私密路径、旧运行回执、旧实验版本或旧工作区脚本。

独立实现证据：先写规范与行为测试；采用全新数据契约和模块；只使用 Python 标准库，可选调用独立安装的 SQLCipher；保留第三方 notices；公开经验只描述聚合故障模式，不含原文。

## 13. 已验证与待实战验证

合成数据上应验证：授权门、逐行覆盖、引用拆分、脱敏、不可变 release、accepted 不重跑、租约回收、白名单修复、依赖门、拆包、冲突与人工裁决、KB 批准门。

待实战验证：macOS/Windows 微信 4.x 不同小版本的实际目录、schema、加密参数、用户依法提供 key 后的解密、真实规模性能、跨模型召回量表和真实知识库连接器。所有这些接口默认 fail closed，并有标准导出回退。完整分项见 `docs/feature-implementation-matrix.md`。
