# Knowledge Base Rules

本仓库是面向多个 Agent 的共享知识库。Markdown 与 Git 是事实源，GBrain 是可重建的检索与关系派生层。

## 1. 读取与检索

- 默认检索结果层：`project`、`decision`、`methodology`、`synthesis`、`concept`。
- 检索先覆盖全局结果，再对与当前任务 `modules` 相同的页面加权；模块是权重，不是硬隔离墙。跨模块命中仍可返回，但必须说明迁移条件。
- 任务开始时优先检查相关的活跃 `decision`。新建议若与既有决定冲突，必须说明是在执行旧决定，还是已经命中 `revisit_when`。
- `source` 默认不进入事实回答。核验出处、寻找候选思路、比较观点或结果层不足时可以检索 evidence scope，但必须把命中标成来源观点、案例、宣传主张或待验证假设。
- `maturity: seed` 只能提供候选动作、访谈问题、文案灵感或实验假设；不得作为稳定事实、普遍规律或高风险决策的唯一依据。
- `.raw/` 不进入常规检索，也不能直接作为结论。
- Lab 305 的内容复盘继续由 Lab 305 Content OS 管理；只有其正式导出的、经过隐私过滤和知识库审批的结果才进入本库。普通对话复盘不得替代或污染 Lab 305 的专用复盘。

## 2. 写入审批

- 读取、搜索和提出建议不需要审批。
- 新增、修改、移动、合并或删除任何知识页、Raw、链接、frontmatter、Schema 或 GBrain 配置前，必须生成精确提案并获得用户对具体提案的明确批准。
- 自动提取、分类和蒸馏只能形成草稿或提案，不能直接写库。
- Schema 变更单独审批，不夹带普通内容变更。
- 已批准的写入由知识网关完成校验、Git 提交、GBrain 同步和图谱重建；索引失败只修复派生索引。
- 不运行无人值守的 `gbrain dream` 或 `gbrain autopilot`。

## 3. 统一 Intake 路由

任何材料先经过同一初筛，再决定是否保存：

1. 判断输入形态：普通对话复盘、电话/访谈、外部视频或文章、书籍、随笔/Idea、项目材料，或专用系统导出。
2. 判断是否需要保留 Raw；Raw 保留原文、转录、改口和缺失，不润色，不进入默认检索。
3. 识别 `provenance_class`、`source_family`、利益关系和可复原路径。
4. 把材料拆成事实、来源观点、Agent 推断、宣传主张、可借鉴话术和待验证假设，不得混写。
5. 标记一个或多个 `modules`。模块只改变权重，不改变全局可发现性。
6. 先查重，再决定更新既有页面、建立 Source、建立结果页，或不保存。

## 4. 三层结构

- `.raw/`：未经清洗的原始材料，保留可复原性，不进入 GBrain。
- `source`：证据分析与候选观点池。可以暂时没有结果页；不得为了满足链接门槛把 n=1 观点包装成方法。
- 结果层：只有已经形成未来可直接使用的项目事实、承诺、方法、综合或概念才进入。

不新增 `candidates/`。一份连贯来源对应一张 Source 页；同一来源里的不同观点使用稳定的 `claim_id`。五个观点可以分别晋升为五张互不依赖的结果页，也可以全部停留在 Source。

## 5. Source 与可信度

- Source 标题只表达中性的语义主题。作者、平台、账号、原始标题和营销措辞放在元数据与出处区，不进入标题或别名。
- `derived_pages: []` 合法；有派生结果时，`evidence` 与 `derived_pages` 仍须双向一致。
- 候选观点必须写明：`claim_id`、陈述、claim 类型、直接依据、样本与来源家族、利益关系、允许用途、禁止用途、反证和下一步验证。
- `maturity`：
  - `seed`：单一来源或单次事件，只能低权重使用。
  - `corroborated`：至少一个真正独立的来源家族、独立事件或用户自己的运行形成交叉支持。
  - `validated`：在明确范围内经过重复运行、对照或高质量证据验证。
- 同一作者、同一机构、转载链和相互引用不算独立来源。重复发布不能把观点自动升级为事实。
- 话术可被标记为“可借鉴表达”，同时把其事实主张标记为不可用于决策。
- 医疗、法律、财务、人物稳定模式、精确事实和强因果声明不因 `seed` 而降低门槛。

## 6. 结果层分发

- 当前项目事实、目标、约束和仍有效状态 -> `project`
- 已承诺且会持续约束未来行动的重要选择 -> `decision`
- 可按步骤重复执行、带边界和失败条件的流程 -> `methodology`
- 多个独立证据共同支持、能排除选项或改变判断的结论 -> `synthesis`
- 多次参与判断且不属于前四类的稳定机制 -> `concept`

结果页按“未来如何被 Agent 使用”分类，不按平台、作者、媒介或话题分类。

## 7. Decision 的触发与消费

`decision` 不是审批日志、建议清单或讨论流水。只有同时满足以下条件才独立建页：

1. 用户已经明确承诺，而不是表达偏好。
2. 会影响不止一次后续行动。
3. 忘记它会导致重复争论、返工、成本、风险或行为冲突。
4. 存在至少一个被放弃的真实替代方案。
5. 能写清适用范围与 `revisit_when`。

临时选择留在对话；项目级小决定更新 Project 的当前约束；跨时间、跨任务或高影响承诺才建立 Decision。页面必须包含最终选择、理由、拒绝方案、影响范围、实施位置、`decision_status` 与重审条件。被替代、撤销或过期时更新原页并使用 `supersedes`，不新建“最终版 2”。

## 8. 收录与维护

- 优先更新已有页面，避免同义页和碎片化互链。
- `related`、`evidence`、`derived_pages` 的非空值必须使用带引号的
  Obsidian 内部链接，并优先写完整路径，例如
  `related: ["[[projects/pronto-apparel-ai]]"]`；不得写成普通 slug。
- 结果层必须能改变未来 Agent 的回答、判断或动作，并写明边界、失效条件或最后确认时间。
- Source 可以只保存候选观点；收藏夹、新闻剪贴和未清洗素材仍不能冒充正式结果。
- 现有页面缺少新字段时不自动假定为 validated 或 global；在被更新或迁移时补齐。
- 写入后必须运行 Vault 校验、schema validate/lint、GBrain 同步、图谱同步和索引范围检查。
- `ops/`、`.raw/`、根 README 和依赖文档不得进入用户知识图谱或默认检索。

## 9. 活页面与周期审计

- Project 和其他明确标记为持续状态的页面是活页面，不是一次入库后冻结的成品。它们可以在项目推进中持续修正目标、状态、约束、证据和待定项。
- 页面没有专属 Agent 所有权。任何 Agent 都可以读取并提出增量更新，但不得直接改写；仍须经过查重、精确提案和用户批准。
- 更新活页面时保留当前有效状态，明确新增、改变和失效的部分；不得把任务流水、未确认推断或整段聊天追加进去。
- 每次状态更新同步维护 `updated`；Project 同步维护 `last_confirmed`，并指出该日期之后不能自动推断的内容。
- 周期性全库审计检查格式一致性、重复页、冲突结论、失效状态、标题污染、断链和证据边界。审计默认只报告并生成分项提案，不自动清洗，不把多个独立问题打包成一次模糊授权。
- 外部专用系统仍可作为某些页面的事实源。例如 Lab 305 Content OS 与 Obsidian 冲突时，以其正式导出契约为准；本库只保存获准同步的结果。

## 10. Schema 演进

新增页面类型前，必须同时证明它有不同的默认检索行为、不可由 metadata 表达的独有契约，以及至少三个真实样例。否则优先扩充 metadata。所有迁移先做样本 dry run，再逐步迁移，不因规则升级一次性重写全库。
